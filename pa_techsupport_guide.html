Palo Alto NetworksのTech Support Fileは、ファイアウォールの設定やシステム状態、セッション、ルーティング、カウンタ、各種プロセスログなどをまとめて取得した診断データです。

本記事では、Stractoの検証環境で使用しているPalo Alto Networks PA-200から取得した実際のTech Support Fileを基に、通信障害の切り分けでどこを確認するのか、Management PlaneとData Planeをどう考えるのかを、図を交えて分かりやすく整理します。

Tech Support Fileとは

Tech Support Fileは、Palo Alto Networksファイアウォールの状態を一式まとめた診断用データです。単一のログではなく、設定、各種showコマンドの結果、システムログ、プロセスログなどがひとつのアーカイブに集約されています。

今回使用した検証機のデータには120個のファイルが含まれており、通信障害だけでなく、CPUやメモリ、HA、VPN、GlobalProtect、認証など幅広い観点を確認できます。

POINT 01現在の状態

Interface、Session、Route、ARP、Policy、各種Counterから、その時点の稼働状態を確認できます。

POINT 02時系列の情報

System Logやdaemon logを使い、異常が起きた時間帯にどのプロセスで何が発生したかを追えます。

POINT 03切り分けの材料

「通信できない」という事象を、経路・Policy・Session・Drop Counterなど複数の観点から分解できます。

どんな情報が入っているのか

Tech Support Fileは、ファイアウォールの内部状態を複数のカテゴリから確認できるようになっています。今回の検証データにも、以下のような情報が含まれています。

Management PlaneとData Plane

PAの障害解析では、まず管理系の処理と実際の通信を処理する部分を分けて考えると整理しやすくなります。

GUIへ入れない、Commitが遅い、ログ処理が重い、といった事象はManagement Plane寄りです。一方、通信できない、Sessionが生成されない、Packet Dropが増えている、といった事象はData Plane側の確認が重要になります。

通信障害ではどこから見るか

Tech Support Fileは情報量が多いため、最初からすべてのログを読むより、通信の流れに沿って確認する方が効率的です。

Global Counterは何を見るためのものか

通信障害で特に有効なのがGlobal Counterです。PA内部でパケットがどのように処理され、どの理由でDropされたかを確認する手掛かりになります。

STEP 01事象を再現
STEP 02Counterの増分を見る
STEP 03Drop理由を絞る

今回の検証データにも、PolicyによるDropや経路に関係するカウンタ、TCP処理に関係するカウンタなどが含まれています。ただし、カウンタが存在するだけで障害原因と断定するのではなく、発生時刻・通信条件・Session・Route・Policyと合わせて判断することが重要です。

Global Counterは「犯人を一発で特定する画面」ではなく、PA内部で何が起きているかを絞り込むための材料として使います。

代表的なdaemon log

Tech Support Fileには、機能ごとのプロセスが出力するログも含まれます。事象に応じて対象ログを絞ると、解析しやすくなります。

MANAGEMENTmp-monitor.log

Management PlaneのCPUやメモリなど、管理系リソースの状態を確認する際に使います。

DATA PLANEdp-monitor.log

Data Plane側の稼働状況や負荷を追う際に確認します。

VPNikemgr.log

IKE/IPsec VPNのネゴシエーションやSA確立に関する調査で使用します。

AUTHENTICATIONauthd.log

認証処理に関する事象を確認する際に使います。

HIGH AVAILABILITYha_agent.log

HA状態、フェイルオーバー、同期などを確認する際の主要ログです。

LOGGINGlogrcvr.log

ログ受信・処理系の状態を確認するときに利用します。

DNSdnsproxyd.log

DNS Proxy機能に関連する問題の切り分けに利用します。

WEB / SSL VPNappweb / nginx logs

管理WebやSSL VPN系のWebサービス状態を追う際に確認します。

障害解析のイメージ

たとえば「特定の通信だけ通らない」という事象であれば、以下の順で見ると整理しやすくなります。

01Interface

対象インターフェースがUpか。エラーやDropが増えていないか。

02Route / ARP

宛先へのRouteがあるか。Next HopのARPが解決しているか。

03Policy / NAT

Source、Destination、Service、Zone、NAT条件が想定通りか。

04Session

Sessionが生成されているか。送受信の方向やStateに違和感がないか。

05Global Counter

事象再現時に増えるDrop理由がないか。

06関連ログ

System Logや対象daemon logの時刻を合わせ、イベントを確認する。

この順序で確認すると、「ネットワークそのもの」「設定」「PA内部処理」のどこに問題がありそうかを段階的に絞れます。

Tech Support Fileを扱う際の注意点

Tech Support Fileは障害解析に有効な一方、公開・共有時には注意が必要です。今回の記事では、検証機の実データをそのまま掲載せず、内容を一般化しています。

  • シリアル番号や機器固有IDは公開しない
  • 実IPアドレス、MACアドレス、ホスト名はサンプル値へ置き換える
  • ユーザー名、認証情報、鍵、証明書などは掲載しない
  • 実際のSecurity Policyや構成から環境が特定できないよう一般化する
  • ログの一部を掲載する場合も、時刻や識別情報を必要に応じて加工する

まとめ

Tech Support Fileは、PAの障害解析に必要な情報を一式確認できる非常に有用な診断データです。ただし、重要なのはファイル数の多さではなく、事象に応じて見る場所を絞ることです。

通信障害であれば、Interface → Route / ARP → Policy / NAT → Session → Global Counter → 関連ログ、という順序で確認すると、原因候補を効率よく絞り込めます。

監視サーバが「異常を見つける」役割だとすれば、Tech Support Fileは「なぜ異常になったのかを深掘りする」ための材料です。両者を組み合わせると、監視から原因解析までの流れが見えやすくなります。

記事について

本記事は、Stractoの検証用途で使用しているPalo Alto Networksファイアウォールから取得したTech Support Fileを基に、公開可能な内容へ一般化して構成しています。

元データにはシリアル番号、IPアドレス、MACアドレス、ホスト名、設定情報、ユーザー情報、証明書・鍵など公開に適さない情報が含まれるため、記事では具体値を掲載していません。また、Tech Support Fileの内容やコマンド出力はPAN-OSのバージョンや機種によって異なる場合があります。
